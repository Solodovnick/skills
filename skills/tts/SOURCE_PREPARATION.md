# Подготовка источника

## PDF → Markdown

Для текстового PDF сначала используй MarkItDown:

```bash
markitdown input.pdf > raw.md
```

Сохраняй `raw.md` как неизменяемый сырой экспорт. Повторный запуск на том же PDF полезно сравнить по SHA-256: детерминированный результат упрощает аудит.

Используй Poppler для независимой проверки:

```bash
pdfinfo input.pdf
pdftotext -layout input.pdf extracted.txt
pdftoppm -f 1 -l 5 -r 144 -png input.pdf page
```

Рендери обложку, оглавление, обычную страницу, таблицу, страницу с формулами/сносками и финальную страницу. Если PDF сканированный или извлечение пустое, переключайся на OCR, а не пытайся чинить пустой Markdown.

## Очистка

Создавай отдельный чистый Markdown, не перезаписывая сырой экспорт. Проверяй:

- повторяющиеся колонтитулы и номера страниц;
- оглавление, продублированное в основном тексте;
- потерянные заголовки;
- переносы слов между строками;
- таблицы, превратившиеся в бессмысленную последовательность;
- URL, стрелки, проценты, математические знаки и дефисы;
- порядок абзацев в многоколоночной вёрстке.

Для TTS не обязательно сохранять визуальную таблицу. Нужна однозначная линейная формулировка: сначала название таблицы, затем строки как короткие предложения. Не удаляй содержательные данные только потому, что ASR хуже работает на таблицах.

## Структура сценария

Разделяй книгу по реальным смысловым заголовкам, а не по физическим страницам. Для каждой главы храни:

- порядок;
- заголовок;
- путь к тексту;
- число символов и слов;
- SHA-256;
- исходный диапазон или страницу, если это возможно.

Перед синтезом проверь, что сумма текстов глав покрывает чистый сценарий без пропусков и перестановок.

Разделяй три независимых утверждения: PDF успешно извлечён, очищенный сценарий полностью покрыт главами, а перевод/редактура верны относительно оригинала. Хэши и покрытие доказывают первые два, но не подтверждают точность перевода или авторской редакции.

## Произношения

Держи две версии словаря:

1. Неакцентированные фонетические замены для реального TTS.
2. Акцентированные формы только для лексического аудита.

Применяй замены от длинных ключей к коротким и ограничивай границы слова, иначе `AI` может испортить более длинный термин. Сохраняй регистровые варианты, если они реально встречаются.

Для русского технического текста полезно заранее нормализовать:

- английские аббревиатуры и названия букв;
- смешанные конструкции вроде `CI/CD`, `PR/FAQ`, `A2A`;
- номера уровней `R0`, `L3`;
- бренды и фамилии;
- символы `/`, `%`, `→`, `+`, которые могут склеивать соседние слова.
