# Батчевый контроль качества

## 1. A/B-тест разметки ударений для Qwen3-TTS

Перед длинным прогоном синтезируй один и тот же короткий русский фрагмент минимум в трёх вариантах:

- обычный текст;
- комбинируемый знак ударения `U+0301`;
- плюс перед ударной гласной.

В одном реальном прогоне Qwen3-TTS Base 8-bit дал следующие WER независимого Whisper:

- обычный текст: `0.0000`;
- комбинируемые ударения: `0.6957`;
- плюс-разметка: `2.0435`.

Это эмпирический результат, а не вечное свойство всех моделей. Повторяй тест при смене модели, версии, голоса или языка. До успешного теста не размечай весь корпус.

## 2. Лексический аудит RuAccent

RuAccent используй на копии текста. Затем перенеси только позиции ударений обратно на исходные символы и проверь:

- число русских токенов не изменилось;
- после удаления ударений текст совпадает с исходником;
- символы `/`, `%`, `→`, дефисы и формулы не склеили слова;
- для многосложных слов покрытие каждого финального батча не ниже 0.98.

Некоторые версии RuAccent и ONNX Runtime требуют `token_type_ids`; если вход модели их ожидает, добавляй нулевой массив формы `input_ids`. Перед RuAccent заменяй неподдерживаемые символы пробелами только в аналитической проекции, затем собирай результат поверх нетронутого исходника.

## 3. Независимый ASR

Не проверяй TTS той же моделью или тем же внутренним представлением. Практический независимый проверяющий для Apple Silicon:

```text
mlx-community/whisper-large-v3-turbo-8bit
```

Для каждого батча сохраняй:

- ожидаемый текст;
- распознанный текст;
- сырой WER;
- нормализованный WER;
- сырое и нормализованное покрытие слов;
- профиль текста и порог;
- аудиохэш;
- флаг предупреждения.

## 4. Нормализация и пороги

WER без нормализации даёт много ложных тревог на `SDD` против `эс-ди-ди`, цифрах, дефисах и таблицах. Применяй один словарь алиасов к ожидаемому и распознанному тексту.

Нормализуй только заранее описанные эквиваленты: пунктуацию, регистр, числа и произношения аббревиатур. Не применяй лемматизацию, стемминг или удаление русских окончаний: это скроет ошибки рода, числа, падежа и времени. Для контроля склонений сохраняй сырой токенный diff рядом с нормализованным WER и отдельно поднимай замены русских слов с похожей основой, но разными окончаниями.

Телефонные цифры сопоставляй с исходным номером в контексте номера: Whisper может объединить группы цифр, а обычное правило `num2words` ошибочно прочтёт их как целое число. Не включай режим чтения цифр для всех чисел книги. Если Whisper дописал типовую фразу на тишине, удаляй её только из расчётной копии транскрипта после проверки хвоста аудио. Сохраняй сырой транскрипт, правило и версию нормализации, а также хэш WAV; не скрывай этим реальный пропуск или повтор речи.

Для спорного хвоста сопоставь транскрипт с временными метками и повторным распознаванием короткого конца WAV. Если выводы расходятся или в хвосте слышна речь, оставь предупреждение для прослушивания. Одна типовая фраза Whisper сама по себе не доказывает, что её произнёс TTS; отсутствие фразы в одном повторном ASR также не доказывает тишину.

Для обычных чисел подставляй в расчётную копию ASR форму из манифеста только при точном совпадении цифр и единственном произнесённом варианте в текущем фрагменте: `100 → ста` может быть правильнее общего `сто`. Так же сопоставляй написание аббревиатуры с произнесёнными буквами только при подтверждении исходным фрагментом, например `RTMS` и `рТМС`. Фиксируй каждую замену в QC; не заменяй похожие на слух неизвестные слова.

Рабочие стартовые пороги:

| Профиль | Максимальный нормализованный WER |
|---|---:|
| Обычная проза | 0.18 |
| Обложка/титульный блок | 0.35 |
| Технический текст с аббревиатурами | 0.50 |
| Таблица или структурированный список | 0.65 |

Для всех профилей нормализованное покрытие слов должно быть не ниже 0.85. Порог WER не отменяет покрытие: короткий или повторяющийся транскрипт может иметь обманчивую метрику.

Не определяй таблицу только по числу исходных строк: переносы после PDF-конвертации делают обычную прозу многострочной. Требуй структурные признаки таблицы/списка и после аудита смотри распределение профилей. Если большинство корпуса внезапно получило самый мягкий порог, считай классификатор подозрительным и перепроверь его до сборки.

Назначай профиль каждому батчу по его содержимому. Глава с обычной прозой может содержать плотный список препаратов: порог прозы для такого батча даст ложные тревоги на написании названий, а мягкий порог для всей главы скроет ошибки в соседней прозе. Для медицинских названий сохраняй сырой ASR и проверяй спорное произношение на слух; фонетический алиас сам по себе не подтверждает правильную речь.

## 5. Ремонт низкого покрытия

Если покрытие ниже 0.85:

1. Полностью декодируй исходный WAV, проверь длительность и прослушай место предполагаемого обрыва.
2. Повтори независимый ASR на коротких окнах того же WAV, например по 10–12 секунд, сохрани временные границы, сырые транскрипты и хэш записи. Длинный список может быть произнесён до конца, хотя Whisper обрывает транскрипт целого файла.
3. Если речь в исходном WAV действительно пропущена или повторена, раздели текст по строкам, предложениям или перечислениям, синтезируй короткие сегменты отдельно и склей их с паузами.
4. Повтори Whisper-проверку итогового ремонтного WAV и сохрани причину, прежнее покрытие, число частей и новый хэш. Если обрыв оказался только артефактом ASR, зафиксируй это отдельно и сохрани предупреждения о спорных словах до слуховой проверки.

Если модель повторяет аббревиатуру, используй локальную замену только в этом батче. В одном глоссарии повтор `ИИИИ…` исчез после деления на шесть частей и локальной замены `и-и → эй-ай`.

## 6. Финальная блокировка

До сборки мастера должны выполняться все условия:

```text
stress_audit.status == passed
stress_audit.failed_batches == 0
asr_warning_count == 0
technical_failures == []
asr_blocking_failures == []
```

Это критерии **проверенного финального мастера**. Если пользователь явно запросил раннюю сборку при оставшихся ошибках:

1. Снимай согласованный набор батчей и QC-отчёт на момент сборки: идентификаторы, хэши WAV, версии сценария и модели, открытые предупреждения и блокирующие ошибки.
2. Собирай в отдельный каталог и называй файлы и метаданные так, чтобы версия была явно обозначена как непроверенная. Не заменяй готовым MP3 список ошибок и не отмечай QC как пройденный.
3. Полностью декодируй MP3, проверь длительность, порядок частей, теги и хэши. Техническая проверка файла не закрывает ошибки речи.
4. Если параллельно идёт ремонт, собирай только из зафиксированного снимка. Новые WAV и результаты ASR относятся к следующей версии; проверенный мастер можно выпустить после полного QC отдельно.

После сборки проверь каждый файл полным декодированием:

```bash
ffmpeg -v error -i book.mp3 -f null -
```

Также проверь FFprobe-данные, длительность, число каналов, sample rate, bitrate, теги и SHA-256. Скрипт `scripts/validate_audio.sh` автоматизирует базовую часть.

## 7. Честная интерпретация

RuAccent + Whisper — сильный автоматический фильтр для пропусков, повторов, окончаний и грубых искажений. Он не доказывает идеальную интонацию и не заменяет человеческое прослушивание омографов, фамилий и спорных ударений. Отчёт должен явно различать автоматический и слуховой контроль.

Whisper не выдаёт позиции ударений. Поэтому фраза «ударения проверены автоматически» означает только: акцентный анализ текста выполнен, словоформы не изменены, а ASR услышал ожидаемые слова. Чтобы утверждать, что ударение действительно произнесено верно, нужна слуховая проверка каждого спорного места или отдельный акустический детектор ударений.

После точечной правки `+` сохраняй хэши WAV до и после пересинтеза. Если QC-предупреждение об ударении исчезло, а WAV побайтово совпал с прежним, исправилась только текстовая разметка контроля: слышимое ударение не изменилось. Такой фрагмент оставляй для слуховой проверки; не записывай его как исправленный в аудио.
